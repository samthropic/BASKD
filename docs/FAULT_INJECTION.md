# Fault injection

HW2 extra credit: inject latency, errors and timeouts behind the provider adapter, run the
shared conformance checks under each fault, and show which guarantees hold.

## How the faults are injected

Everything runs through the shared `CalendarService` interface (`baskd.contract`) and our real
`GoogleCalendarProvider`: its `_execute`, `translate_http_error` and write handling. Only the
Google SDK is replaced, by a stateful fake Google Calendar
([`tests/faults.py`](../tests/faults.py)) that behaves like Google for the calls we make: ids
on insert, `404` for an unknown id, `status: cancelled` after a delete, and `410` for a second
delete. A fault sits between the adapter and that fake, and acts at one of three points:

| Stage | Meaning | Example |
| --- | --- | --- |
| `before` | The request never reaches Google | token refresh fails, DNS fails, a `429` |
| `after` | Google applies the request, then the answer is lost | a timeout or `503` after an insert |
| latency | Google answers correctly, but slowly | 50 ms on every call |

| Fault | What it does |
| --- | --- |
| `none` | Baseline, no fault |
| `latency` | Every Google call answers correctly after 50 ms |
| `token-refresh` | Token refresh fails on every call; nothing reaches Google |
| `dns` | DNS lookup for Google fails on every call |
| `rate-limit` | Google answers `429 rateLimitExceeded` without acting |
| `revoked-key` | Google refuses the service account's credentials |
| `read-timeout` | Every `events.get` times out; writes are fine |
| `write-applied-then-timeout` | Google applies each insert and update, then the answer times out |
| `write-applied-then-503` | Google applies each insert and update, then answers `503` |
| `delete-applied-then-reset` | Google applies each delete, then the connection resets |

The live counterpart of these runs on staging: a revision with a 1 ms Google timeout
(`docs/OBSERVABILITY.md`, "Making a provider failure on purpose"), used for the Level 3
walkthrough and the Level 4 alert drill (`docs/SLO.md`).

How to read it:

- **Latency changes nothing.** All 24 checks pass with 50 ms on every call.
- **Each fault breaks only what it should.** `read-timeout` fails only the checks that read.
  The write faults fail only create and replace. `delete-applied-then-reset` fails only
  `delete_removes_event`: the delete raises `provider_unavailable` even though Google applied
  it. "Cleanup hit the fault" means the check passed and the suite's own teardown
  delete then met the fault.
- **The last 16 rows always pass.** Those checks bring their own controlled failures (the
  suite's `failing_service` fixture), so they hold regardless of the injected fault. They
  check request validation and the five shared errors.

## Which guarantees hold

[`tests/unit/test_fault_injection.py`](../tests/unit/test_fault_injection.py) runs in every
CI build and asserts, for each of the 10 faults and each of create, get, replace and delete,
the exact error and whether the write happened:

| Guarantee | Holds? | How the test shows it |
| --- | --- | --- |
| 1. A failure is always one of the five shared codes, never an unhandled exception | Yes, under all 10 faults | Every operation either succeeds or raises `CalendarError` with the documented code |
| 2. `retryable: true` only when the write did not happen | Yes | For every retryable create or replace, the fake calendar is unchanged |
| 3. When a write's outcome is unknown, it may really have happened, so it is not retryable | Yes | Under `write-applied-then-*`, create and replace are `provider_error`, `retryable: false`, and the fake calendar *did* change |
| 4. Latency changes nothing but time | Yes | The shared suite passes unchanged under `latency` (`TestSharedSuiteUnderLatency`) |
| 5. A client that retries only retryable failures never creates a duplicate | Yes | One create during the fault, a retry after it clears only if `retryable`: exactly one event, for `token-refresh`, `rate-limit` and both write faults |
| A repeated delete is safe | Yes, by design | Under `delete-applied-then-reset` the delete is reported retryable; a retry returns `not_found` ("already gone", shared rule 5) |

**The tests can catch a regression.** Disabling the unknown-outcome rule in
`providers/google.py` (treating a write's lost answer as retryable) makes 5 checks fail,
including guarantee 5: the client retries and creates a second event.

**What this does not cover:** latency long enough to hit the real 10 s socket timeout. The
fake raises the timeout itself; the real path was exercised on staging with a 1 ms timeout.

## Running it

```bash
uv run pytest tests/unit/test_fault_injection.py              # the guarantees, as in CI

```
